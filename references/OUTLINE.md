# OUTLINE — 章節切分心法：敘事職責 + 密度／語義判斷切 step（SRT 可選校準）

> 給 AI agent 的章節規劃方法論。目標：把 `SCRIPT.md` 產出的收斂稿
> `script.md`，切成「幾個章節、每章幾個點擊 step」，寫進各章
> `narrations.ts`——這是點擊翻頁前的最後一道規劃，也是**唯一**決定畫面會有
> 幾屏、每屏放多少字的地方。
>
> 概念源自 video-podcast 類文稿工具的實戰經驗（section 按敘事職責、beat 從
> 口語流長出、用真實停頓切段），本文件已把它完整吸收改寫為這個 skill 自帶
> 的方法論——**不需要安裝任何外部 plugin 就能照著做**。

流程定位：`article.md`（素材）→ `SCRIPT.md`（心法）→ `script.md`（收斂後的
連貫口播稿）→ **本檔案（OUTLINE.md）** → 各章 `narrations.ts`（step 數真相
源）→ 逐章開發（見 `GUIDE.md`）。

`script.md` 收斂定稿時，會附帶兩項中繼資訊——`topic_definition`（受眾／語
氣／範圍／目標時長，見 `SCRIPT.md` §0）與每個 section 的密度等級（見
`SCRIPT.md` §1.4）。**這兩項連同章節規劃一起，寫在實際專案的 `outline.md`
起手式**；本檔案只講方法，不重複定義格式。

---

## 1. 敘事職責制切分（§C.2）

### 1.1 章節按「在敘事裡幹嘛」定，不是套公式

規劃章節時，每一章要回答的問題是：**「這一章在整篇敘事裡負責做什麼？」**
常見的敘事職責（依主題調整，不是清單裡選好選滿，也不是每章都要出現）：

| 敘事職責 | 這章在幹嘛 |
|---|---|
| 開場 | 讓聽眾知道「這與我何干」，願意繼續聽下去 |
| 全景 | 給整體地圖，讓後面的細節有地方掛 |
| 核心 | 這次真正要講的主張／發現／機制，通常不止一章 |
| 案例 | 用具體事例把核心論點釘實 |
| 收束 | 收回開場提出的問題，給出可帶走的一句話 |

一章可以只對應一個敘事職責，也可以是「全景＋核心」這種複合章——**由內容
的份量和轉折點決定切在哪，不是先決定要幾章再回頭填內容**。

### 1.2 明確反對：3~8 步 × 總時長÷30 的硬公式

`web-video-presentation:OUTLINE-FORMAT` 用的機制是「每章 3~8 步、
`章數 ≈ 總時長 ÷ 30 秒`」——**這個機制被本方法論丟棄，不採用**。原因：

- **數量／時間公式切章，邊界是湊出來的，不是內容邏輯決定的**。同一段推理
  過程，若份量剛好落在公式門檻邊緣，會被迫「硬湊滿 3 步」或「硬砍成 8
  步」，而不是「這段內容天然需要幾步講完」。
- 時長反推步數，等於用一個跟內容無關的數字（分鐘數）去決定應該切幾刀，
  和 `SCRIPT.md` §2.4 反對的「湊時長灌水」是同一種病根——只是這次湊的是
  「步數」而不是「字數」。
- 真正該決定「切幾步」的是**密度**（§2）和**真實停頓**（§3），不是時鐘。

丟掉公式之後，多章節之間份量會自然不均——這是預期行為，不是要修正的
缺陷：全景章天生比案例章短，案例章天生比全景章長，硬拗成一樣長反而是
灌水或閹割內容。

### 1.3 章名（`registry/chapters.ts` 的 `title`）要短——它是頁腳導覽標籤

每章的 `title` 會直接顯示在底部**章節進度條**的膠囊裡（等寬鋪滿全寬）。所以：

- **`title` 是短把手，不是完整句**。目標 **≤ 6 個字**（中文），例如
  `開場`、`全景`、`主力產品`、`收束`。完整的描述性框架（「本月主軸」「ecs-ten
  驗測修正」這種）放在**該頁的眉題／主標**（章節開場頁 step 0 自己寫），
  不塞進 `title`。
- **不要用 `A · B` 的長複合當 title**（如 `開場 · 本月主軸`）——那會在等寬膠囊裡
  被截成 `…`。要嘛只留短的那半（`開場`），要嘛換一個更短的詞。
- **章數也要克制**：進度條膠囊等寬平分全寬，章越多每格越窄；**章名長度要隨章數
  遞減**（5 章可到 6 字，8 章就要壓到 3～4 字）。§4 的「章數別爆」同此理。

一句話：`title` 短到能在一個膠囊裡一行放得下、不被截，就對了；想寫多的話，寫進頁面本身。

## 2. 密度分級表

`script.md` 交接過來時，每個 section 已經標好密度等級（`SCRIPT.md`
§1.4）。切 step 時沿用同一張表，**數值與 `SCRIPT.md` 完全一致**，這裡不
重新定義，只補「怎麼接到投影字級階」這一層：

| 等級 | 每 section 建議 step 數 | 適用場景 | 每屏字量傾向 | 常用字級 token |
|---|---|---|---|---|
| Impact | 1 | 全篇/全章的關鍵一擊——一個數字、一句結論、一張圖，獨佔一屏才有份量 | 極少（一句話或一個數字） | `--t-display-1/2`、`--t-h1` |
| Standard | 2–3 | 一般論述段：鋪陳 → 主張 → 一句收束 | 中等（一兩句 + 一個支撐點） | `--t-h2`、`--t-lead`、`--t-body` |
| Compact | 4–6 | 需要拆解步驟或多個並列小點的段落 | 較少但多屏（每屏一個小點） | `--t-h3`、`--t-body`、`--t-label` |
| Dense | 6+ | 資訊量本身就大的段落（如逐項案例、多維度比較），寧可拆多屏也不要擠 | 每屏更少字、靠多屏攤開 | `--t-body`、`--t-label`（絕不縮小到低於 `--t-micro` 地板） |

**分級越高不代表畫面越滿**——反而相反：等級越高（Compact/Dense），代表
內容量大到必須拆更多屏，每一屏能放的字反而要更少，才能守住 `GUIDE.md`
§6.1 的投影字級地板（body ≥26px、label ≥22px、micro ≥20px）。密度分級
表決定的是「切幾屏」，不是「字可以縮多小」——**字級地板不因密度等級而
下修，超出的內容一律靠加 step，不靠縮字**。

## 3. 切 step：密度＋語義判斷（底線），SRT 為可選增強

### 3.1 底線做法：靠密度＋語義判斷切點（不需任何工具）

密度分級（§2）回答「這段大概切幾屏」；實際切在哪一句之間，靠 agent 對稿子的
**語義判斷**——哪裡是講者自然停頓、轉折、進入下一個聚焦想法的位置就切；逗號級
換氣、或切開後前後語意站不住的位置不切。**這是底線，實測 agent 純判斷切段就
足以產出節奏合理的 deck，不需任何工具。** 判斷同時看兩件事（都要滿足）：

1. **自然停頓／轉折**：一個聚焦想法講完、要進下一個 = 候選切點；純換氣（逗號級、
   語意沒講完）不算，別見到標點就切。
2. **密度帶寬**：切出的 step 數落在該 section 密度等級（§2）的建議帶寬附近。若一段
   講得太趕（沒喘息點）卻判為 Dense，**回頭檢查稿子是不是該加停頓**，別在沒停頓
   處硬切製造假分屏。

語意完整優先：某處即使讀起來像停頓，切開後前後兩半各自站不住（「因為 A｜所以 B」
硬切），就往前後找語意完整的邊界。切好之後：把每個 step 的文字段落寫進該章
`narrations.ts`（`narrations.length === 該章 step 總數`，唯一真相源，不可動搖）→
要有聲時再跑現成逐步音頻 pipeline（`npm run extract-narrations` →
`npm run synthesize-audio`，`PRESENTATION_TTS=edge`，介面不變）。

### 3.2 可選增強：用真實語音停頓（SRT）校準

純文字判斷偶爾難確定「這句到底有沒有明顯停頓」。想更精準時，可**選擇性**產出
真實語音的時間戳來校準——這是增強，不是必經步驟：

    （可選）對某章連貫稿跑 scripts/script-to-srt.sh <章節稿檔案>
       （薄封裝，預設 edge-tts；輸出 <name>.mp3 + <name>.srt/.vtt）
     → agent 讀 SRT 的真實停頓長度，對照 §3.1 的判斷校準切點（判準見 §3.3）

**不跑 SRT 也完全可以——§3.1 的判斷就是底線；跑了 SRT，就多一層真實停頓的
客觀依據。** 決策記錄：spec §C.5 原採「Option Y／SRT 必產」，實測 agent 純判斷
切段也做得好，故降為可選增強、判斷切段當底線。

### 3.3 怎麼讀 SRT 判斷切點（**選擇用 SRT 校準時**的判準）

若你走 §3.2 的可選校準、拿到了 SRT，agent 逐句／逐詞看時間戳，交叉兩個訊號做
判斷，**兩者都要看，不是只看一個**：

1. **停頓長度**：句子／子句之間的無聲間隔明顯拉長（比逗號級的呼吸停頓更
   長、更像講者刻意換一口氣或轉折），是候選切點。純逗號級的短停頓（講者
   只是換氣，語意還沒講完）**不算**切點，不要見到 SRT 裡任何間隔就切。
2. **密度分級的參考帶寬**：這段 section 標的是 Impact/Standard/Compact/
   Dense（§2），實際切出來的 step 數應該落在該等級的建議帶寬附近。如果
   SRT 上找不到夠多的自然停頓、但密度判定為 Dense，代表這段話可能講得
   太趕（連貫成一整段沒有喘息），這時候**該回頭檢查是不是稿子本身該加
   停頓**，而不是在沒有停頓的地方硬切一刀製造假分屏。

判斷時要同時滿足「語意讀起來完整」——即使 SRT 某處有停頓，只要那個位置
切開後前後兩半各自語意不完整（例如「因為 A [停頓] 所以 B」中間硬切，
「因為 A」自己站不住），就不該切在那裡，往前後找語意完整的邊界。

### 3.4 明確聲明：SRT 是判斷依據，不是自動裁刀

**本方法論不建自動切段演算法**——不寫一支腳本讀 SRT 的停頓長度、套一個
毫秒閾值、自動吐出切點清單。原因：

- 停頓長度只是**線索**之一，語意完整性、密度帶寬、章節敘事節奏都要一起
  權衡，這是需要理解內容的判斷，不是單一數值門檻能覆蓋的規則。
- 自動演算法一旦切錯（比如把換氣停頓誤判成語意斷點），錯誤會直接寫死進
  `narrations.ts`，沒有人在迴圈裡覺察；讓 agent 讀 SRT 做判斷，等於把
  「有理解力的判斷者」留在迴圈裡，遇到 SRT 訊號和語意衝突時能自己識破、
  回頭調整，而不是機械套用一條規則產出看似合理、實則斷錯的切點。

這是本方法論選的路線（**Y-assist**：無論靠純語義判斷（§3.1 底線）還是用 SRT
校準（§3.2 可選），切點都由 agent 判斷、不交給自動演算法，比一支自動切段器穩）——比自動演算法多一點人工／agent 介入的成本，換來切點踩對語意邊界
的準確度，且 agent 判斷能順帶抓出「稿子這段講太趕該補停頓」這種自動
演算法看不出來的問題。

## 4. 每章 step 數參考帶寬（§C.7 丙）——參考，不是規則

丟掉「每章 3~8 步」的硬公式（§1.2）之後，完全不給任何數字又太空——容易
出現「這章明顯只有一句話的份量卻硬撐五步」或「這章塞了三個案例卻只給一
步」而沒人察覺。這裡給一個**非硬性的健檢用參考帶**，用法和角色都跟硬公式
不同：

| 用途 | 硬公式（已丟棄） | 這裡的參考帶 |
|---|---|---|
| 決定切幾步的依據 | 章節數量／總時長反推 | 密度分級（§2）＋ 語義判斷（§3；SRT 可選校準） |
| 這個數字拿來做什麼 | **規則**：切出來的步數必須落在範圍內才算合格 | **健檢**：算出來的步數明顯超出範圍時，回頭檢查是不是內容份量沒抓對 |
| 落在範圍外怎麼辦 | 硬湊或硬砍到符合 | 允許超出；只是提醒去覆核一次「這章是不是太薄／太重」 |

**參考帶（一般章節）**：一章通常由 1～3 個敘事職責段落組成（例如「全景＋
核心」或單一「案例」），把各段依密度分級（§2）算出的建議 step 數相加，
落在**大約 4～12 步**是常見範圍：

- **明顯低於下限**（如整章只有 1～2 步）：檢查是不是這章其實該併進相鄰
  章節，或是內容份量不夠撐一個獨立敘事職責——除非這章本身就是刻意設計
  的 Impact 型單擊重章（見 §2 表格，這種情況 1 步是合理的，不是缺陷）。
- **明顯超過上限**（如整章衝到 20 步以上）：檢查是不是這章其實該拆成
  兩章——一章塞太多敘事職責，容易讓聽眾抓不到「這一章到底在講哪一件
  事」。

**再次強調**：這個帶寬只是切完之後回頭覆核用的健檢門檻，**不是驗收標準
也不是新公式**——不能拿它反推「這章密度分級應該怎麼標」或「這章該有幾個
敘事職責段落」。真正決定步數的永遠是 §2 的密度＋§3 的語義判斷（SRT 可選校準）；這個帶寬
只負責在算出來的結果明顯失衡時，提醒回頭想一想，不強制改動。

## 5. 這份文件跟其他檔案的關係

- **上游**：`SCRIPT.md`（文稿心法，提供收斂後的 `script.md` ＋ 密度分級
  ＋ `topic_definition`，本文件直接沿用不重複定義）。
- **下游**：各章 `narrations.ts`（step 數真相源，本文件切 step 流程的
  最終產出）與 `scripts/script-to-srt.sh`（§3.2 的 SRT 產生工具）。
- **平行**：`GUIDE.md`（章節開發鐵則、視覺／動畫規範、投影字級階
  `--t-*` token）——本文件只管「切在哪一屏」，不管「那一屏長什麼樣子」。

概念源自 video-podcast 類文稿方法論的實戰經驗，但本文件已是完整、可獨立
操作的版本——不需要另外安裝任何 plugin，也不依賴任何外部 skill 才能照著
執行。
