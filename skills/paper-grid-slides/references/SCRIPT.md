# SCRIPT — 口播稿心法：寫稿、去 AI 腔、對抗式收斂

> 給 AI agent 的文稿方法論。目標：把 `article.md`（素材/出處）寫成一份**唸出來
> 像真人在講話**的口播稿 `script.md`，再交給 `OUTLINE.md` 切成點擊 step。
>
> 方法論骨幹的哲學源自 video-podcast 類文稿工具的實戰經驗（先語言後點擊、
> section 按敘事職責、不套鉤子模板），本文件已把它完整吸收改寫為這個 skill
> 自帶的方法論——**不需要安裝任何外部 plugin 就能照著做**。

> **文風規範不在本檔案，在 `references/TONE.md`。** 本檔案管的是「怎麼寫、
> 怎麼收斂」的流程與機制（語氣定調、對抗式 critic 迴圈、密度分級、TTS 預檢）；
> 「字怎麼用」——人稱、動詞、禁用表達、標題寫法——一律以 TONE.md 為準。
> 兩份衝突時以 TONE.md 為準。

流程定位：`references/ALIGN.md`（口述構想 → 人類可讀對齊骨架）→ `article.md`
（素材）→ **本檔案（SCRIPT.md）** → `script.md`（收斂後的連貫口播稿）→
`OUTLINE.md`（敘事職責切分 + 切 step）→ 逐章開發。

**全新主題、使用者只有口述構想、還沒有 `article.md`**：先跳到
`references/ALIGN.md`，收斂出一份人類可讀的對齊骨架、經使用者確認後，
才展開成 `article.md` 進入本檔案的流程——不要跳過對齊骨架，直接把口述
內容展開成完整的 `article.md`/`script.md`/`outline.md` 三份長文件，那樣
使用者要挑錯時只能對著 AI 產出的完整成品挑，修正成本高很多。

**若已有一份 `script.md`、使用者說不滿意要重寫**，先跳到 §0-A（校準意圖），
確認具體要修的方向和層次之後，才進入 §0 動筆——不要在還沒定位問題出在敘事
/深度/語氣哪一層之前，就直接開始寫新版稿子。

---

## 0-A. 重寫既有稿子前：先校準意圖，不要直接動手改

**這一節只在「已經有一份 `script.md`，使用者說不滿意、要重寫」時觸發**——
從零開始寫新稿直接跳到 §0。「不滿意」是最容易被 agent 誤判的訊號：使用者
說「內容不太佳」時，可能是敘事骨架整個錯了，也可能只是某幾句話的語氣不像
本人——這兩種問題的修法天差地遠，猜錯方向重寫一輪等於白工。

### 0-A.1 用分層問題縮小範圍，不要一次要求使用者講清楚

不要問「你覺得哪裡不好？」這種開放式問題——這會逼使用者自己先做完「診斷」
這個困難的工作，但他們往往只有「感覺不對」的直覺，說不清楚具體是敘事、深
度還是語氣的問題。改用**收斂式選擇題**（可搭配 AskUserQuestion 這類結構化
提問工具），一層一層縮小範圍：

```
第一層：整體方向 vs 細節執行
  「是敘事/角度不對（整體方向要換）」
  「是內容深度/取捨不對（方向對，份量不對）」
  「是語氣/表達方式不對（內容都對，讀起來不像你）」

若答案落在「語氣不對」→ 第二層再問具體是哪種語氣問題：
  「太 AI 生成感/套路」
  「過於客氣/迂迴，不夠直接」
  「不夠像我自己的語氣/詞彙」
```

每一層的答案決定要不要問第三層、以及後續怎麼動手。**先問完再動手**——在
定位到具體層次之前寫出來的任何一版新稿，都可能是白工。

### 0-A.2 語氣校準用「真實案例」，不是抽象形容詞

當問題定位到「語氣不像使用者本人」這個層次時，**不要**接著問「你希望是什
麼語氣？直白、正式、還是活潑？」——抽象形容詞對雙方都難以達成共識：使用者
選了「直白」，agent 對「直白」的理解版本、和使用者心裡的「直白」，大概率
是兩個不同的東西。

改成請使用者**口述一段真實想表達的內容**（不用修飾、不用完整句子，想到什
麼講什麼），拿這段口述當校準錨點：

1. 請使用者用自己的話口述一小段（例如整份稿子的開場，或某個核心段落）
   實際想講什麼。
2. Agent 逐項對比「口述版」和「舊稿版」的具體差異——**不是**籠統說「風格
   不一樣」，而是拆解成可指認的差異點：破題方式不同、主軸框架不同、用詞
   直接程度不同、術語迴避程度不同、收尾意圖不同……每一點都要能各自舉出
   兩版的對應句子當證據。
3. 把這份差異列表回報給使用者確認——這一步在把「感覺不像我」翻譯成「具
   體差在這幾點」，讓後面的決策問題有實例可以指認，而不是繼續抽象討論。

### 0-A.3 校準完主軸後才問結構性決策點，且要問到能直接動筆為止

確認大方向（例如「整個敘事框架都要換」）之後，**不要**直接开始重寫——這時
候合理會冒出好幾個結構性決定（新框架要幾段、原本的具體案例段落要不要留、
聽眾定位要不要跟著調整、時長要不要變），這些如果不先問清楚，重寫一版之後
極可能又要因為某個沒問到的決定推翻重來。

用 AskUserQuestion 把這些決策點一次攤開（每題 2–4 個選項、標示推薦項），
逐一問完、確認全部落地之後，才進入 §0 的 `topic_definition` 定調與動筆。
這一步跟 §0-A.1 的分層問題不同：§0-A.1 問的是「問題出在哪一層」，這裡問
的是「新方向底下的具體規格」——兩層問題不要合併一次問，先定性、再定量。

## 0. 動筆前先定調（語氣前置）

**在 writer agent 開始寫第一個字之前**，先把下面這份 `topic_definition` 填好、
和使用者對齊。這是整條產線唯一「兩邊都要看著同一把尺」的地方——writer 和
critic 之後各自獨立工作，靠的就是這裡定下的基準，而不是臨場猜。

```yaml
topic_definition:
  audience: "誰在聽？（如：主管月報聽眾／零基礎技術新人／內部工程團隊）"
  scope: "這次要講的範圍邊界（哪些子題目在內、哪些明確不講）"
  target_duration: "目標時長（如：8 分鐘），用來反推整體字數量級"
  tone: professional | casual        # 用詞冷硬正式 vs 帶點口語鬆弛
  verbosity: concise | detailed      # 每個論點展開的細節深度
```

- `tone` 和 `verbosity` 是**旋鈕**，不是二選一貼標籤：同一件事，
  `tone: casual + verbosity: concise` 寫出來會短、俏皮、跳過鋪墊；
  `tone: professional + verbosity: detailed` 會完整鋪陳因果、用詞收斂。
  兩者組合決定「每段話該有多長、可以多隨性」。
- 這份定義寫進 `outline.md` 的起手式（和章節規劃放一起），但**寫稿
  (writer) 和挑錯 (critic) 都要先讀它**——critic 抓的不是「這句話好不好」，
  而是「這句話符不符合我們說好的語域」。沒有這把尺，critic 會用自己預設的
  審美去改稿，改出來的版本可能離題。
- 目標時長只是量級參考，不是拿來反推「每頁字數公式」——密度怎麼分配見 §1.4。

**本 skill 的語氣預設（重要）**：預設走**平實、客觀**——不用 mic-drop 金句收尾、
不用個人化戲劇句或誇張比喻、不用露骨誇獎（中肯陳述優點即可）。收尾的份量來自
前面論證累積出的實質結論，不來自最後一句話的修辭。**若講者本人偏好戲劇化語氣
或金句收尾，那是要在上面 `topic_definition` 校準時主動 opt-in 的風格選項，不是
預設、也不是品質加分。**

這個預設不是本檔案自己定的，而是 `TONE.md` §4「結尾在內容說明完以後直接結束，
不另外添加感悟或價值總結」在口播場景的具體化。**動筆前 writer 和 critic 都要
先讀完 TONE.md**——`topic_definition` 的 `tone`／`verbosity` 旋鈕調的是詳略與
鬆緊，調不動 TONE.md 的事實邊界與禁用表達，那些在任何旋鈕位置都成立。

## 1. 骨幹：先語言，後點擊

### 1.1 段落服從語言，不服從點擊機制

**先把稿子當一段連貫的話寫完，寫的時候完全不要想「這句要不要單獨成一
click」。** 想清楚一個意思要花三句話才講得順，就寫三句連著的話；一句話就能
講完，就別硬拆成三段湊點擊數。

這是本方法論唯一的「反直覺」規則，值得說明為什麼：如果你邊寫邊想「這是不是
該切一個 click 了」，你的注意力會被切割動作綁架，句子就會被迫變短、變碎，
讀起來一頓一頓、失去語言原本的呼吸感（像被打斷的人在講話）。**切 step 是
`script.md` 定稿之後才做的事**（見 `OUTLINE.md`），寫稿階段完全不用管。

### 1.2 section = 敘事職責，不是格式配額

規劃大架構時，每個 section 要回答「**這段在敘事裡負責做什麼**」，而不是套
「開場/中段/結尾各佔幾步」的公式。常見的敘事職責（依主題調整，不是清單裡
選好選滿）：

| 敘事職責 | 這段在幹嘛 |
|---|---|
| 開場 | 讓聽眾知道「這與我何干」，願意繼續聽下去 |
| 全景 | 給整體地圖，讓後面的細節有地方掛 |
| 核心 | 這次真正要講的主張／發現／機制 |
| 案例 | 用具體事例把核心論點釘實 |
| 收束 | 收回開場提出的問題，給出可帶走的一句話 |

一個 section 該有幾步、佔多長，交給密度分級（§1.4）和內容本身的份量決定，
不是先射箭再畫靶。

### 1.3 開場：不套三鉤子模板

常見的「懸念／反差／利益」三選一開場鉤子，聽起來像刻意的行銷話術——尤其是
月報、內部技術簡報這種場合，硬套鉤子只會顯得假戲劇、標題黨。**這裡不提供
模板**，只守兩條所有人都同意的底線：

- **不清嗓**：禁止「大家好，今天來跟大家聊聊…」這種開場白暖場式廢話。
  第一句話就要進入內容。
- **不 PPT 標題感**：禁止開場第一句是名詞短語式的標題朗讀（如「本季度營運
  概況與挑戰」），那是投影片的標題，不是人講出來的第一句話。

好壞怎麼判？**不是看有沒有套對鉤子模板，是看「一個真人聽了這句開場，會不
會想繼續聽下去」**。這個判準比任何模板都準——套對了模板但聽起來假，一樣是
壞開場；沒套模板但一句話就讓人好奇，就是好開場。

### 1.4 密度分級：決定每屏字量

`script.md` 寫完、要切 step 之前，先給每個 section 定一個密度等級，這決定
「這段內容適合攤開成幾屏、每屏放多少字」。分級越高不代表越好，**要對應這段
內容本身的資訊量**——一句話講得完的結論硬要分四屏鋪陳，是灌水；反過來把
需要五個轉折的推理硬塞進一屏，是超載。

| 等級 | 每 section 建議 step 數 | 適用場景 |
|---|---|---|
| Impact | 1 | 全篇/全章的關鍵一擊——一個數字、一句結論、一張圖，獨佔一屏才有份量 |
| Standard | 2–3 | 一般論述段：鋪陳 → 主張 → 一句收束 |
| Compact | 4–6 | 需要拆解步驟或多個並列小點的段落 |
| Dense | 6+ | 資訊量本身就大的段落（如逐項案例、多維度比較），寧可拆多屏也不要擠 |

這張表只決定「切幾屏」的參考帶寬，不是字數公式；實際切 step 的邊界依據
`OUTLINE.md` 的密度＋語義判斷（§3；SRT 為可選校準，非必經）。
放進本檔案是因為密度等級要在**寫稿完成、進入切 step 前**就先標好，屬於
`script.md` 交接給 `OUTLINE.md` 時附帶的中繼資訊。

### 1.5 破題結構與平實收尾（技術分享／方法論類簡報適用）

這一節是一種**可選的敘事風格**，不是所有簡報都要套——當講者本人的說話習慣
偏向技術分享、方法論陳述（例如「不是要介紹某個工具，而是要講一套做事方法」
這種定位），下面三個結構性特徵值得留意。這些是從真實使用者口述稿裡萃取
出來、且經確認符合他本人語氣的結構，**不是新造的模板**——套用前務必先用
§0-A 的方式跟使用者對過，不要預設每個人都吃這一套。

- **先鋪陳一個聽眾會認同的現況觀察，再轉出真正的問題意識**：不是一上來就
  丟結論或標題，而是先講一段大家都感受得到的背景（「工具越來越多、
  更新越來越快」），讓聽眾先點頭，再順勢帶出「但真正的問題其實是……」。
  這跟 §1.3 反對的「清嗓廢話」不同——這段鋪陳本身要有內容（具體的現況
  觀察），不是「大家好，今天想跟大家聊聊」這種純暖場語句。
- **收尾平實、不要 mic-drop 金句（本 skill 預設）**：全篇或全章結束前，用
  平實的陳述句把重點自然收束就好——**不要**刻意丟一句「精煉到可以單獨貼上
  投影片、脫離上下文也成立」的金句作結。判準倒過來：收束句**需不需要**靠
  「金句感」撐場？如果內容本身夠實，平實講完就夠了。這條是 `TONE.md` §4
  結尾規定在口播場景的具體化。
  **例外（opt-in）**：講者本人明確偏好金句收尾時，才在 §0 校準時講好、當成
  這份稿子的風格選項打開，不是預設。
  **地雷提醒**：即使 opt-in 了金句，也最容易順手套用 §2.1 排除的「不是A而是B」
  排比句型（例如「這不是技術問題，而是方法論問題」）——這類句子讀起來像現成
  金句、寫起來很順手，但正是 `TONE.md` §5 要清除的模板腔，一樣要過 §2.1 的
  逐句檢查，不因為它是「金句」就豁免。
- **技術詞彙直接點名，不做過度防禦性包裝**：技術分享的聽眾本身有能力
  消化術語，不需要每個專有名詞都包一層「這只是示意」「這不代表已上線」
  的防禦性語句。防禦性措辭有它的適用場合（例如對主管做風險敏感的正式
  匯報），但套用到技術分享語境會顯得畏首畏尾、稀釋掉內容的直接程度——
  該不該用防禦性包裝，取決於 §0 `topic_definition` 裡定的聽眾與場合，
  不是預設值。

### 1.6 全篇路線圖 + 收尾回顧（可選，另一種敘事骨架）

跟 §1.5 一樣是**可選的敘事骨架**，不是所有簡報都要套——結構是「開場先
給整篇路線圖（有哪幾個段落、各自在講什麼）→ 各段落按順序展開 → 收尾
回頭點名每個路線點，做簡短回顧，加深記憶」。這種骨架讓聽眾從一開始就
有地圖，中途不會迷路；代價是開場會先暴露大綱，少了「留到後面才知道」
的懸念——技術分享／教學類簡報通常適合，需要懸念或戲劇性轉折的簡報則
不適合，取決於 §0 `topic_definition` 的聽眾與場合，套用前務必先用 §0-A
的方式跟使用者對過，不要預設每個人都要這種「先劇透路線、後面逐一
兌現」的骨架。

套用時落在兩個具體位置：

- **開場段落的收尾**：不只是 §1.3 講的「轉出問題意識」，而是明確列出
  接下來幾個段落的路線（例如「① 這是什麼、有什麼優點 → ② 跟同類選項
  比較 → ③ 實際用起來的心得」），這段本身就是開場的收束，不需要另外
  再鋪陳一次「今天要講的主題是」這種重複句。
- **收尾段落**：先簡短回顧路線圖裡的每一點各自的結論或一句話重點，讓
  聽眾把整篇內容串起來；回顧每一點時用詞要跟開場路線圖的用詞呼應（同
  一個詞前後兩次出現），聽眾才聽得出「這是在回應開場說的那個路線」，
  不是隨口又提一次。**收束就落在回顧的最後一點上、平實結束即可**——預設
  不另外加一句 mic-drop 金句（見 §1.5；除非講者已 opt-in 金句風格）。

### 1.7 條目式報讀（可選，第三種敘事骨架）

跟 §1.5、§1.6 一樣是**可選骨架**，套用前一樣要先跟使用者對過。結構是「每一
段只報條目與數字，一個條目一句摘要，不展開因果——聽眾想聽哪一項的細節，
當場提問，講者再口頭延展」。

**適用場合**：定期例行報告（月報、週報、進度同步），聽眾是主管或同儕，
**與講者同處一個會議室、能隨時打斷提問**。這個骨架的成立前提是「延展發生
在問答，不在投影片上」，所以：

- **不適合單向播放**（錄影、非同步分享、講者不在場的 deck）。沒有人能問，
  條目就只是條目，聽眾拿不到任何理解。
- **不適合需要說服的簡報**。條目不承載論證；說服要靠 §1.5 的破題結構，或
  `GUIDE.md` §6.4 的「證據 > 評分」。

跟另外兩種骨架最大的差別在 `topic_definition`：這個骨架**必須配
`verbosity: concise`**，而且 concise 的理由不是「內容不多」，是「詳略的
決定權交給聽眾」。稿子刻意短是設計選擇——值得在 `script.md` 裡寫一行註記
說明，免得後續維護的人（或另一個 agent）誤判成內容不足而去「補充」。

套用時落在四個具體位置：

- **每一段的組成**：一組並列條目，每條「名稱 + 一句摘要 + 日期／標籤」。
  摘要只講「這條做了什麼」，不寫為什麼、不寫影響——因果留給問答。
- **每一段至少一個數字視覺**：純條目清單連續好幾頁會讓聽眾失去焦點，每段
  要有一個「可以停下來看」的數字（hero-num 對撞、長條圖、計票、網格點亮）。
  數字的出處規則不變（`GUIDE.md` §6.2）。
- **開場給路線圖，但不給總量數字**：路線圖照 §1.6 的做法列出各段落。實測
  踩過的坑：開場就丟「本月投入 402.7 小時」這種總量，聽眾還沒有任何段落
  可以掛這個數字，讀起來突兀。**量化留到最後一段**——那時候各段內容已經
  講完，數字才有對照的參照點。
- **收尾平實結束**：一句「以上是某月的工作彙整」即可。**不要**再加逐段
  回顧——前面各段剛報完條目，回顧是同一批資訊的第二次播放。這一點與 §1.6
  相反：那個骨架的回顧有價值，是因為前面各段展開了因果，回顧才是壓縮。

**密度分級的落點**（§1.4）：各段落多為 Compact（4–6 步，一條目一拍逐項
揭示），數字視覺頁為 Impact（1 步獨佔）。整份 deck 的拍數通常低於同題材的
展開型稿子，這是預期行為，不是切得不夠細。

**這個骨架與「內容單薄」的分界線**：判準是「有沒有可延展的底料」。每一條
條目，講者都要能在被追問時往下講三到五句；如果講者自己也只知道那一句
摘要，那不是骨架選擇的問題，是素材蒐集不足——回頭補 `article.md`。

## 2. 保留條款：讓文字像人話

不管密度、不管敘事職責怎麼分，下面這幾條是**任何一版稿子都要守**的底線。

### 2.1 反 AI 腔六類必清

**本表是 `TONE.md` §5「不使用的表達」在口播稿場景的操作化版本**——同一套標準
的兩種形式，不是兩套規則。TONE.md 給的是規則本身，這張表給的是反例與改法，
方便 critic 逐句對照（見 §3.3）。

逐句自查（也是 critic 逐句獵殺的主要目標，見 §3），這六類是重災區：

| 類別 | 長怎樣 | 反例 | 改法 |
|---|---|---|---|
| 假共情 | 用「我懂你的感受」式語句製造親近感，但空洞、無具體對象 | 「我知道大家平常都很忙，處理這些真的很辛苦」 | 刪掉，或換成具體的共同經驗（「上季度我們都被這張報表卡過」） |
| 假深刻 | 用抽象大詞包裝其實很普通的觀察 | 「這背後反映的是整個系統性的結構問題」 | 直接講是什麼問題（「這是因為兩個團隊各自維護一份設定檔」） |
| 自我標榜／露骨誇獎 | 稿子自誇講得好、有洞見，或對某個對象（方案、工具、自家專案）露骨吹捧 | 「接下來這個發現非常關鍵」「這是它的功勞」 | 刪掉判斷詞與吹捧，改中肯陳述——好不好、重不重要聽眾自己判斷（中肯講優點勝過露骨誇獎） |
| 萬能模板 | 放進任何主題都成立的空話，換個主題照樣能用 | 「在這個快速變化的時代」「不論規模大小的團隊都會面臨」 | 刪掉，或換成這個主題**專屬**才成立的具體描述 |
| 排比堆砌 | 用「不是A而是B」「既要…又要…」三連發湊氣勢 | 「這不是一次調整，而是一次升級；不是修補，而是重建」 | 挑其中真正想講的那一句，其餘刪掉 |
| 戲劇腔／金句 | 用個人化煽情句、誇張比喻、或 mic-drop 金句製造戲劇效果與刻意記憶點 | 「差到連我自己都不想登入」「押錯就回不去的豪賭」「唯一反悔不了的，是按下註冊那一刻」 | 改成平實客觀的陳述，讓事實自己有份量（本 skill 預設平實；金句／戲劇化須講者於 §0 主動 opt-in） |

**唯一判準**：這句話**唸出來**，一個真人在這個場合會這樣說話嗎？——不是
「這句話文法通不通」「邏輯對不對」，是「人真的會用嘴巴講出這句話嗎」。假
共情、假深刻這些之所以踩雷，正是因為它們在紙面上讀起來通順，但唸出來會
覺得彆扭、造作。判斷時建議真的唸出聲音讀一遍，眼睛看不出來的問題，耳朵聽
得出來。

### 2.2 句子與人稱

以 `TONE.md` §2（事實和敘述身分）與 §3（用詞和句子）為準，以下是口播場景
最常用到的幾條：

- 一句話盡量只講一件事；需要轉折就斷句，不要用從屬子句疊從屬子句。
- 句子長短要有變化。不要連續堆疊碎句，也不要把多個判斷壓進結構複雜的長句。
- **動詞要準確**：不用含義含糊、可以自然替換的單字動作詞（搞、弄、寫、看、
  查、改、做、用、點、跑），改用「整理、處理、編寫、查看、檢查、修改、完成、
  使用、點擊、執行」。「是、有、能、會」等必要詞語不需要機械替換；固定搭配
  只有在替換後仍然自然時才改寫，不要為了避開單字而製造生硬的書面表達。
- **人稱**：說明自己的專案、做法和判斷時用「我」；面向聽眾討論一般情況時
  優先用「我們」，直接稱呼聽眾群體可以用「大家」。只有明確指導聽眾完成具體
  操作時才用「你」。同一段內不要頻繁切換稱呼。

> **這一節在 2026-08-03 改過**：舊版寫的是「能用『你』就用『你』」與「口語詞
> 優先於書面語」，兩條都與 TONE.md 相反，現已改掉。值得一提的是，本 repo 唯一
> 的完整口播稿範例（`example/01-service-flow/`）本來就全篇使用「我／我們」、
> 一次「你」都沒有出現——這次是讓規範追上既有實作。

### 2.3 數字、專名、英文術語——單獨審一遍

這三類是 TTS 唸錯的重災區，**在稿子定完之後、進 critic 迴圈之前，額外過
一遍**（和一般的反 AI 腔審查分開做，因為檢查的維度不同——這裡看的是「唸
出來會不會錯」，不是「聽起來像不像人話」）：

- **數字**：格式是否清楚（年份/百分比/版本號會怎麼唸？見 §4.2）。
- **專名**：人名、地名、產品名有沒有破音字或非常規唸法。
- **英文術語**：中文夾雜的英文詞，是整詞唸（如 "Notion" 唸英文）還是要
  拆解唸（如 "API" 逐字母），稿子裡沒寫清楚 TTS 會亂猜。

這一遍的產出直接餵進 §4.1 的 `phonemes.json` 預檢表。

### 2.4 信息保留（軟化版）

video-podcast 類方法論常見「摘要不能少於原文 60% 信息量」這種硬比例，
這裡**刻意不採用**——比例是死的，內容密度是活的，同一比例套進不同主題會
時而寬鬆、時而過嚴。改用兩條可操作、但不綁死數字的判準：

1. **別為了湊時長灌水**：如果一段話存在的理由只是「讓這章不要太短」，
   刪掉它，不要因為目標時長沒到就硬塞。
2. **關鍵事實／數字／論證鏈逐項對得上**：回頭比對 `article.md`，稿子裡
   出現的每一個關鍵事實、數字、因果推論步驟，要能在素材裡找到出處且沒有
   被過度摘要到失真。這裡看的是「有沒有漏掉不該漏的乾貨」，不是「字數夠
   不夠多」——防的是「摘要摘到只剩結論、中間的推理過程被磨掉」，讓聽眾
   聽完只記得結論卻不知道為什麼。

## 3. 自動對抗 critic 迴圈（核心機制）

### 3.1 為什麼要對抗，不是自己改自己

> **核心主張**：「第一版不理想」的解不是叫 AI 寫更好，也不是逼人重寫，
> 而是讓一個獨立 critic 去聽另一個 agent 的聲音——**AI 聽不見自己，但聽得見
> 別人**。

寫稿的 agent 在生成文字時，優化的目標是「這段話讀起來通順、邏輯完整」，
而不是「這段話唸出來像不像人在講話」。這兩個目標大部分時候重疊，但反 AI
腔的雷（§2.1 那六類）恰好是「讀起來通順、但唸出來假」的重災區——正因為
通順，寫稿的 agent 自己檢查不出問題。叫同一個 agent 自己重讀一遍、自己
改，效果有限：它會傾向於**護自己的草稿**（找理由說服自己這樣寫沒問題），
而不是真正推翻重寫。

解法是換一雙耳朵——**用另一個 agent 當這雙耳朵**，而不是同一個 agent 回頭
看自己的產出。

### 3.2 流程

```
⓪ topic_definition + tone/verbosity（§0，已在動筆前定好）
        ↓
① writer agent：讀 article.md + §0 定調 + §1/§2 全套法則，寫 v1 稿
   （接受它不完美——這是迴圈的起點，不是終點）
        ↓
② critic agent（全新 context，沒看過 writer 的思考過程，不護短）
   依 §3.3 rubric 逐句獵殺，標記問題 + 給出建議修法
        ↓
   writer agent 依標記重寫 → 產出下一版
        ↓
   （②③循環，見 §3.4 輪數規則）
        ↓
③ 收斂後：人閘門（輕量，§3.5）—— 使用者唸一遍 wince test
        ↓
④ 定稿 script.md + 敘事職責 outline，交給 OUTLINE.md 切 step
```

**執行方式**：主 agent 自己 spawn 一個獨立的 critic subagent（乾淨
context，只給它 §0 的 topic_definition 和待審稿子，**不給它 writer 的
草稿過程或修改理由**）。critic 的輸出只回頭交給 writer agent，**不要讓
writer agent 自己讀完 critic 意見後又自己扮演 critic 二次確認**——那樣又
繞回「同一個聲音審自己」的老問題。整個迴圈是主 agent 自動跑的，中途不需要
使用者介入（使用者只在事前決定輪數、事後做最終驗收）。

### 3.3 Critic Rubric（逐句獵殺清單）

critic agent 收到稿子後，**逐句**過一遍，對每一句話問：

1. **六類 AI 腔**（§2.1 表格）：這句話落在假共情／假深刻／自我標榜或露骨
   誇獎／萬能模板／排比堆砌／戲劇腔或金句的哪一類嗎？另外對照 `TONE.md`
   §5（不使用的表達）與 §4.1（標題寫法）——§2.1 的表格是 TONE.md §5 的
   操作版，但 TONE.md 還有幾條表格沒收進去的規則（群體判斷開頭、引號代替
   強調、標題冒號後半句的口號），一樣要抓。
2. **真人會這樣講嗎**：把這句話唸出聲音，一個真人在這個場合、對著這群
   聽眾，真的會用這個詞、這個句式講這句話嗎？
3. **被摘掉的乾貨**（信息保留軟化版，§2.4）：這句話是不是把 `article.md`
   裡一個有價值的細節／數字／推論步驟摘到只剩結論？聽眾聽完這句話，還能
   不能重建作者為什麼這樣主張？
4. **人工分段痕跡**：這句話讀起來像不像「為了湊一個 click 而被硬切出來的
   碎片」？常見信號：
   - 句子長度異常整齊劃一（像格式湊出來的，不像自然口語有長有短）
   - 每段結尾都用相似的收束句式（「這就是…」「由此可見…」反覆出現）
   - 句與句之間沒有承接詞、邏輯跳躍生硬，像是本來連貫的一段話被剪斷
5. **清嗓開場 / PPT 標題感**（僅對開場句適用，§1.3）：這句是不是用「大家
   好，今天來聊聊…」這類暖場廢話開場？或是用名詞短語式標題朗讀開場？

對每一個踩雷的句子，critic 要標記**類別**（上述 1–5 哪一種）+ **具體
建議**（不是只說「這句不自然」，要給出怎麼改或起碼指出改的方向）。

### 3.4 迴圈輪數：預設 2 輪，開跑前問使用者，硬上限 4 輪

- **預設 2 輪**：writer → critic → 重寫 → critic → 重寫，跑兩趟 critic
  審查後停下。這是大多數稿子「收斂到堪用」所需的量級。
- **開跑前先問使用者要幾輪**：在 §0 topic_definition 對齊時一併問
  （「要跑幾輪對抗迴圈？預設 2 輪」），使用者可以調高或調低。
- **硬上限 4 輪**：不管使用者要求多少輪，最多跑 4 輪就停，並回報「已達
  上限，若還有殘留問題需要人工介入」——避免無限打磨燒 token、也避免
  critic 迴圈本身變成另一種「規定化」陷阱（過度打磨會磨出新的萬能模板腔）。
- 如果稿子在**輪數用完之前**就已經沒有新的獵殺項（critic 交回「無新增
  問題」），提前結束迴圈，不用硬跑滿輪數。

### 3.5 收斂後：先跑 linter，再進人閘門

迴圈跑完不代表可以直接進 OUTLINE.md，還有兩道關。

**第一道（機器）**：對定稿的 `script.md` 跑一次文風檢查。

```bash
python3 skills/paper-grid-slides/scripts/tone-lint.py <專案>/script.md
```

這支腳本是 `TONE.md` §9 指定的檢查器（純標準庫、簡繁通吃）。它只能識別
**已知的**壞表達，抓不到事實錯誤，也判斷不了「唸出來像不像人話」——所以它
擺在 critic 迴圈之後、人閘門之前，是補網不是替代。有 FAIL 就照提示改掉再跑。

**第二道（人）**：請使用者把定稿的 `script.md` **唸一遍出聲**（wince test：
唸到哪一句會「皺眉／卡住／覺得不像自己會講的話」就是還沒過關）。

這一步刻意設計得「輕」：驗收的是**已經被 critic 打磨過的稿子**，不是搶救
一份生肉草稿——如果 critic 迴圈做得確實，人閘門通常只是快速通過確認，不
應該變成又一輪大改。如果 wince test 發現大量問題，代表 critic 迴圈本身
沒抓到位，該檢討的是 rubric 或輪數，而不是叫使用者自己動手改稿。

## 4. TTS 連帶帳（甲）——文稿定稿之後、TTS 合成之前

以下兩項在 `script.md` 收斂定稿、**準備合成語音（TTS，可選——要有聲 deck 或
要用 SRT 校準切點時才跑）之前**執行。這裡處理的是「稿子唸出來對不對」，
不是「稿子寫得好不好」——是文稿產線收尾、交棒給語音合成前的最後一道檢查。

### 4.1 發音預檢：`phonemes.json`

對稿子裡所有**多音字、英文詞、品牌名**做三遍預檢，把結果整理成一份發音
覆寫表，供 TTS provider 在合成時參考（不同 TTS 後端吃法不同——有些支援
SSML `<phoneme>` 標籤直接餵，沒有的話至少作為人工複檢清單，唸錯了手動
換字重跑）。

**三遍預檢，各抓一類**：

1. **第一遍：多音字**——中文裡念法隨語境變的字（如「重」在「重慶」唸
   `chóng`、在「重要」唸 `zhòng`；「行」在「銀行」唸 `háng`、在「行走」唸
   `xíng`）。逐一標出稿子裡出現的多音字，確認語境對應的正確唸法。
2. **第二遍：英文詞**——中文夾雜的英文單字/縮寫，決定是「整詞唸英文音」
   還是「逐字母拼讀」（如 "API" 該逐字母唸 A-P-I，"Notion" 該整詞唸，不是
   逐字母）。TTS 沒有標註時常會兩種都猜錯。
3. **第三遍：品牌名/專有名詞**——人名、公司名、產品名裡藏的非常規唸法
   （創辦人名字的罕見字、音譯品牌名有官方唸法但字面猜不出來的）。

**輸出格式**（供 TTS 前查閱/餵入）：

```json
{
  "overrides": [
    { "text": "重慶",  "reading": "chóng qìng", "note": "多音字：非'zhòng qìng'" },
    { "text": "API",   "reading": "A P I",       "note": "英文縮寫：逐字母拼讀" },
    { "text": "Notion","reading": "英文原音",     "note": "品牌名：整詞唸英文，不逐字母" }
  ]
}
```

存成 `phonemes.json`，跟 `script.md` 放在同一個素材資料夾。TTS 合成前先過
一遍這份表，能覆寫的後端直接吃，不能覆寫的後端就人工複檢對應句子的合成
結果。

### 4.2 數字格式化規則：保留數字 vs 中文唸法

中文 TTS 對數字的預設唸法常常和你想要的不一樣（尤其是大整數會逐字唸還是
唸出「萬/億」分節、電話號碼會不會被當成一般數字唸出計算式的量詞）。定稿
時對照下表，確認每一類數字在稿子裡的呈現方式和期望唸法一致：

| 類型 | 書面呈現（保留） | 建議唸法 | 範例 |
|---|---|---|---|
| 年份 | 阿拉伯數字 | 逐字唸，不當成數量 | `2026` → 二〇二六（不是「兩千零二十六」）|
| 百分比 | 保留 `%` 符號 | 「百分之 X」 | `42%` → 百分之四十二 |
| 版本號 | 保留原格式（含點號） | 逐字母 + 數字分開唸 | `v2.3` → v 二點三 |
| 電話號碼 | 保留分段連字號 | 逐字唸，不當數量詞 | `0912-345-678` → 逐字唸，非「九億…」|
| 大整數（有量級意義） | 依語境可用阿拉伯數字或中文分節詞 | 唸出「萬/億」分節，不逐字唸 | `1,234,567` → 一百二十三萬四千五百多 |
| 序數/編號 | 保留阿拉伯數字 | 「第 X」 | `第3步` → 第三步，不是「第三十步」的誤讀陷阱（確認分隔清楚）|

**原則**：書面呈現盡量維持原格式方便閱讀校對；唸法是額外標註給 TTS 或
`phonemes.json` 用的，兩者不需要長得一樣。如果稿子裡同一類數字反覆出現，
統一寫法比逐一補救更省事。

## 5. 這份文件跟其他檔案的關係

- **上游**：`article.md`（研究蒐證的素材庫，數字/引用/出處都在這，本文件
  不重複規定 `article.md` 怎麼寫）。
- **下游**：`OUTLINE.md`（拿 §1.2 的敘事職責分段 + §1.4 的密度等級，接
  密度＋語義判斷切成點擊 step，SRT 為可選校準）。§1.5／§1.6／§1.7 三種可選
  敘事骨架各自對應 `OUTLINE.md` §1.1 的一段切章指引——選了骨架就去讀那一段，
  三者的開場與收尾做法互相衝突（尤其 §1.6 要逐章回顧、§1.7 明確不要），
  不能混用。
- **平行（文風）**：`TONE.md`——**所有產出文字的文風真相來源**。本文件管
  流程與機制，TONE.md 管字怎麼用；衝突時以 TONE.md 為準。§2.1 的六類表格
  是 TONE.md §5 的口播操作版。
- **平行（視覺）**：`GUIDE.md`（章節開發鐵則、視覺/動畫規範）——本文件只管
  「稿子寫得對不對」，不管「畫面做得對不對」。注意 GUIDE 的「反 AI 味」講的
  是視覺（紫粉漸變、emoji 圖標、假 logo），跟本文件的「反 AI 腔」不是同一件事。

概念源自 video-podcast 類文稿方法論的實戰經驗，但本文件已是完整、可獨立
操作的版本——不需要另外安裝任何 plugin，也不依賴任何外部 skill 才能照著
執行。
