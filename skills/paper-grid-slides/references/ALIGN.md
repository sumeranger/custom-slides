# ALIGN — 從口述構想到人類可讀對齊骨架

> 給 AI agent 的**全新主題起手式**方法論。目標：把使用者一段口語、片段式的
> 主題構想，收斂成一小段**人類可以整段讀完、點頭說「對，就是這個」的對齊
> 骨架**，經使用者確認之後，才展開成 `article.md` 進入 `SCRIPT.md` 的流程。

流程定位：使用者口述構想 → **本檔案（ALIGN.md）** → 人類可讀對齊骨架
（使用者確認）→ `article.md`（素材）→ `SCRIPT.md`（寫稿心法）→
`OUTLINE.md`（切章）→ 逐章開發。

**觸發時機**：全新主題、使用者只給了一段口語構想，還沒有任何
`article.md`/`script.md`/`outline.md`。如果這三份文件已經存在、使用者是
要重寫，直接用 `SCRIPT.md` §0-A，不需要本檔案。

---

## 0. 為什麼需要這一步——`article.md`/`script.md`/`outline.md` 對人不友善

這三份文件是為了餵給 AI 逐章開發設計的，格式、篇幅、術語密度都是給 AI 用
起來順手，不是給人一口氣讀完評估「方向對不對」。如果沒有這一步，流程會
變成：

```
使用者口述構想（片段、模糊）
  → agent 直接展開成完整 article.md + script.md + outline.md（可能上千行）
  → 使用者只能對著這堆長文件挑錯
  → 挑錯成本高：改一個方向可能要牽動三份文件，甚至已經做好的章節元件
```

而這一步要做的是在最前面插入一個便宜的對齊點：

```
使用者口述構想（片段、模糊）
  → agent 收斂成一小段話（通常 200~400 字，一屏能讀完）
  → 使用者讀一遍，點頭或提出修正
  → （可能來回 1~3 輪，成本很低——改的是幾百字，不是三份長文件）
  → 對齊骨架定案
  → 才展開成 article.md，進入 SCRIPT.md 流程
```

這段對齊骨架**不是摘要**——摘要是把已存在的長文壓縮、資訊量減少；這裡是
反過來，`article.md`/`script.md`/`outline.md` 這三份文件當時根本還不存在，
對齊骨架是**先被生出來、資訊量最少但方向已經定案的雛形**，之後才會被
展開、加料成三份完整文件。可以理解成建築的「配置圖」——比藍圖簡單很多，
但格局定了之後，藍圖才有意義；配置圖畫錯，藍圖畫再細都要重來。

---

## 1. 使用者的口述構想通常已經是對的——不要急著重組結構

**最常見的誤判**：以為使用者的口述是「一堆混亂片段，需要 agent 幫忙抓出
隱藏的順序/框架」。實際上多數時候，使用者腦中的順序、因果關係早就想清楚
了（例如：「先了解模型能力、再做 POC、驗證過了才落地，落地要考慮追蹤
評估工具」——這本身就是一條完整的線性敘事），只是用條列式、口語化、跳躍
的方式講出來，**不代表結構本身是亂的**。

這種情況下，agent 真正該做的加工只是**把口語條列擴寫成連貫段落**（加上
「因此」「接著」「當…之後」這類承接詞），**不要**自作主張重新排序、也
不要發明一套新框架去「優化」使用者已經想清楚的順序——這一步做錯，會讓
使用者覺得「你把我的意思講歪了」，比語氣不對更難修正，因為連骨架都要
重談。

先假設使用者的順序是對的，把它讀順、讀出來給使用者看；如果使用者說「不
是這樣」，那才是真的需要重新梳理結構，不要預設每個人都需要 agent 幫忙
重組。

---

## 2. 真正需要 agent 介入的地方：命名/用詞跟業界慣用意涵的落差

使用者口述時常會用一個自己覺得貼切、但業界另有固定意涵的詞來稱呼整個
主題。例如把「一個 AI 專案從發想到落地的過程」稱為「AI Roadmap」——但
「Roadmap」在業界通常指公司導入計畫、技術發展藍圖、產品規劃，跟使用者
實際要講的內容不是同一件事。這種落差如果不處理，後面所有章節的命名、
標題、術語都會繼續建立在一個容易讓聽眾誤讀的地基上，而且會拖到後面才
發現——那時候要改的東西已經很多。

**這是 agent 主動要做的事，不用等使用者問「這樣稱呼對嗎」**：

1. **指出具體落差**：不是含糊說「這個詞怪怪的」，而是講清楚「一般人聽到
   X 會聯想到 A、B、C，但你實際要講的是 Y」，讓使用者看得懂問題出在哪，
   而不是被動接受一個「感覺更好」但講不出理由的替換詞。
2. **給出排序過的候選清單**：列 3–5 個候選命名，每個附一句話說明它貼合
   使用者內容的哪個角度、適合哪種聽眾（技術分享 vs 企業導入等），並給出
   推薦排序——不要只丟一串選項讓使用者自己比較，agent 要先做完篩選和
   排序這個苦工，使用者只需要做最後的取捨判斷。
3. **等使用者選定，不要自己替使用者決定**：候選清單是輔助判斷，最終命名
   由使用者選（或使用者看完候選清單後自己想出更好的、甚至混合兩個候選），
   agent 不要因為自己排了推薦順序就直接採用第一名往下寫。

命名/用詞校正，往往是這一整個對齊步驟裡**槓桿最大的單一動作**——比起
反覆調整段落順序或措辭，一個精準的命名能讓後面所有章節標題、術語表、
封面標語一次到位，不需要回頭補救。

---

## 3. 命名確定後，才展開成連貫骨架段落

術語落差解決之後，才是動筆擴寫：把使用者已確認的順序和內容，用校正後的
命名/術語，寫成一段連貫的骨架文字（通常一屏能讀完，200~400 字量級，不是
完整的 `article.md`）。這一版初稿通常已經相當接近使用者要的東西，因為
結構原本就對、只是換了精確的包裝。

這時候 agent 可以再主動加一點使用者話裡沒直說、但能從內容裡提煉出來的
洞察，作為破題或收尾的亮點——例如從「使用者列出一堆工具名稱」提煉出
「真正的問題不是有哪些工具，而是不知道從哪裡開始」這種痛點句。**但這是
錦上添花，不是必要步驟**，而且提煉出來的句子要明確交還使用者確認「這是
我從你的內容提煉出來的，準不準確」，不要自己認定「這就是使用者的意思」
就直接寫進定案版本——提煉錯了，使用者可能沒發現這是被加進去的東西，
之後在完整稿子裡才第一次注意到，反而拉長對齊的來回。

---

## 3.5 附上一張純文字結構圖，不做真實視覺稿

骨架文字定稿的同時，**額外附一張純文字/Markdown 畫的結構圖**（線性箭頭
鏈、對照表、樹狀結構——依內容形狀選，不強求都用同一種）。原因：骨架文字
是連貫段落，讀起來順但「順序/結構本身對不對」不容易一眼看出來；結構圖
把順序抽出來變成可以單獨審視的形狀，使用者掃一眼就能確認「對，就是這個
順序」或「不對，這兩塊該對調」。

例如线性生命週期類主題，附一條箭頭鏈就夠：

```
💡 Idea
    ↓
🧠 Understand Capabilities
    ↓
🧪 Build a POC
    ↓
🚀 Production
    ↓
📈 Observe / Evaluate / Improve
```

如果內容形狀是對照/取捨（例如「舊命名 vs 新命名」「配角工具 vs 主角
工具」），改用 Markdown 表格；如果是分層架構（例如技術棧），改用縮排
樹狀圖。**挑跟內容形狀最貼近的畫法，不要為了視覺效果硬套線性圖。**

**只做純文字，不做真實視覺稿（配色/字體/動畫）**：這一步的結構圖是用來
驗證「順序/分類對不對」，不是提前預覽投影片會長什麼樣子。真實視覺稿需要
碰 paper-grid 的樣式、元件，成本已經接近逐章開發本身——如果在骨架文字都
還可能被使用者推翻的階段就先做真實視覺稿，一旦骨架改了，視覺稿要跟著
重做，等於白工，違背了 ALIGN 階段「用最便宜的東西對齊」的設計初衷。真正
的視覺呈現，留到 `GUIDE.md` 逐章開發階段——那時候骨架已經定案，值得投入
真正的設計成本。

## 4. 對齊骨架的驗收標準

骨架定案前，用這幾條檢查使用者是否真的可以「一遍讀完、直接點頭」：

- **一屏讀完**：整段骨架長度控制在使用者一次閱讀就能抓住全貌的量級，不
  需要像看 `article.md` 一樣分段消化。
- **順序即敘事**：骨架裡呈現的階段/段落順序，就是之後 `outline.md` 章節
  切分的雛形——如果這裡的順序使用者都覺得怪，後面切章一定會重來。
- **命名已定案**：主標題、核心術語（如「AI Project Lifecycle」這類貫穿
  全篇的關鍵詞）在這一步就要確定，不要留到 `script.md` 階段才發現命名
  不合適——那時候要改的地方已經散落在多個文件裡。
- **結構圖跟骨架文字一致**：§3.5 附的純文字結構圖，順序/分類要跟骨架
  段落完全對應，不是另外畫一套——結構圖是骨架的「形狀摘要」，不是獨立
  的第二份內容。
- **語氣可辨認**：使用者讀這段骨架，會覺得「這聽起來像我會講的話」，還是
  「這是 AI 幫我生的官腔」？如果是後者，這是語氣校準沒做到位的訊號，
  參考 `SCRIPT.md` §0-A.2 用真實案例（使用者親口口述的原話）當校準錨點，
  不要只靠形容詞（「再直白一點」）來回修。
- **文風合規**：骨架本身也是產出文字，一樣要過 `TONE.md`——尤其是事實邊界
  （不要在骨架裡塞使用者沒講過的案例或群體判斷）與標題寫法（§4.1）。

全部通過、使用者明確確認「這就是我要的方向」之後，才進入 `article.md`
的素材蒐集與撰寫，交給 `SCRIPT.md` 的流程接手。

---

## 5. 這份文件跟其他檔案的關係

- **下游**：`article.md`（把這裡定案的骨架展開成有出處、有數字佐證的
  完整素材庫）、`SCRIPT.md`（§0 的 `topic_definition` 直接沿用這裡已經
  確認的受眾/範圍/命名，不需要重新校準一次）。
- **平行**：`SCRIPT.md` §0-A（校準既有稿子的意圖）——本檔案處理的是
  「還沒有稿子、從口述開始」的情境，§0-A 處理的是「已經有稿子、使用者
  不滿意要重寫」的情境，兩者觸發時機不同，不要混用。

概念源自實戰中「先展開完整文件才發現方向錯了、修正成本很高」的教訓：
在成本最低的階段（一小段對齊文字）先把方向定案，比在成本最高的階段
（完整三份文件甚至已完成的章節元件）才發現問題便宜得多。
